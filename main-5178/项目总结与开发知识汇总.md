# X-tapnow 画布项目总结与开发知识汇总

> 总结对象：`X-tapnow-main-workcopy-prompt-5178`  
> 整理日期：2026-07-21  
> 项目类型：基于节点和无限画布的 AI 多媒体创作工作台

## 1. 项目概括

X-tapnow 是一个运行在浏览器中的节点式 AI 创作工具。它把图片、视频、文本、音频等内容表示为可拖拽的节点，通过连线表达上下游关系，再将模型提供商、提示词和生成参数绑定到节点上，形成可视化的创作工作流。

项目的重点不是单次调用某个 AI 接口，而是解决以下问题：

- 在无限画布中组织大量素材、提示词和生成结果。
- 用节点连线复用上游文本、图片或视频，形成连续创作流程。
- 在同一套界面中管理多种 API 提供商和模型。
- 将项目、工作流、生成历史和常用提示词保存在本机。
- 支持批量生成、分镜工程、视频任务轮询和结果下载。

项目采用“本地优先”设计：主要状态保存在浏览器的 IndexedDB 和 localStorage 中，普通使用不依赖项目自带的业务数据库。AI 推理仍由用户配置的远程 API 完成。

## 2. 适用人群与应用场景

### 2.1 适用人群

- AI 图片和视频创作者
- 广告、电商、短视频和影视分镜从业者
- 需要批量试验提示词与模型参数的设计师
- 需要把素材、推理过程和生成结果放在同一空间管理的团队或个人
- 希望接入自建、代理或 OpenAI 兼容接口的开发者

### 2.2 典型场景

1. 上传一张产品图，连接到多个图片节点，批量生成不同构图或不同视角。
2. 将文案节点连接到图片或视频节点，让上游文本自动成为生成输入。
3. 将图片节点连接到视频节点，完成图生视频；将视频连接到视频节点，执行 Remix。
4. 导入 TXT/SRT，利用文本模型拆分分镜，自动生成“剧本 -> 提示词 -> 视频”的节点组。
5. 将多张生成图排版、拼接或合成为一张新图，再送回画布继续生成。
6. 保存工作流模板，在其他项目中复用节点结构和参数。

## 3. 已实现功能

### 3.1 无限画布与节点编辑

- 支持图片、视频、文本、音频节点。
- 支持拖拽移动、调整尺寸、框选、Shift 多选和取消选择。
- 支持鼠标滚轮缩放、空格加拖拽或中键平移、视图复位。
- 支持节点输入/输出端口连线，并可选择、删除连接。
- 支持右键菜单，在鼠标位置创建节点或操作节点、分组。
- 支持复制选中节点，粘贴时重建节点和相关连接。
- 支持删除节点时中止对应的生成任务。
- 支持最多 20 步画布撤销；当前未实现独立的重做栈。
- 支持深色/明亮画布主题和粒子背景。
- 支持自动按媒体比例调整节点尺寸。
- 支持视口裁剪：画面外的普通节点不渲染，以降低大画布压力；视频节点为避免反复加载会持续渲染。
- 支持小地图、缩放百分比和快捷键帮助。

### 3.2 分组与批量执行

- 可将多个节点创建为分组，修改分组名称、颜色、位置和大小。
- 移动分组时可带动组内节点。
- 删除分组时可选择只解散分组或连同内容一起删除。
- 分组支持“全部执行”“只执行视频”“只执行文本推理”等模式。
- 多选节点后可批量生成、打组、下载或送入视觉合成器。
- 批量生成使用工作队列和可配置并发数，默认值为 15。

### 3.3 图片生成与处理

- 支持文生图和参考图生图。
- 支持 Gemini 原生 `generateContent` 图片响应。
- 支持 OpenAI 风格的 Chat Completions、Images Generations 和 Images Edits 接口。
- 可解析 URL、Markdown 图片、Base64、`data:` URL 以及多种非标准嵌套响应。
- 支持一个节点返回多张图片，并在节点内切换当前图片。
- 支持常用比例、1K/2K/4K 分辨率、质量等级和生成数量。
- 支持根据模型 ID 变体自动匹配分辨率和画面比例。
- 支持多个上游参考图；提示词可用 `@图1`、`@图2` 等方式指定实际使用的图片。
- 会构造最终发送给模型的指令，并可在节点中查看最终提示词。
- 支持拖拽、文件选择和剪贴板粘贴图片到画布。
- 支持在浏览器本地抠图，使用 `@imgly/background-removal` 与 ONNX Runtime，无需把原图发送给抠图服务器。
- 抠图优先使用高质量模型，失败时回退到轻量模型，并对透明通道做连通区域清理和边缘优化。
- 支持多角度编辑器，可基于一张参考图按预设角度和模型生成新视角。
- 支持视觉合成器：添加图片和文字、自由排版、设定导出尺寸、导出 PNG，并可把结果送回画布。
- 支持参考图拼接以及选中图片的横向、纵向、网格排列。

### 3.4 视频生成与任务管理

- 支持文生视频、单图生视频和多图参考视频。
- 支持 Sora/OpenAI 风格 `/v1/videos` 任务接口。
- 支持 Veo 统一接口 `/v1/video/create`。
- 支持统一接口 2 `/v2/videos/generations`。
- 支持 Grok 风格视频请求和状态查询。
- 支持 OpenAI 兼容的流式视频生成，解析 SSE/流式文本中的视频地址。
- 支持异步任务轮询、进度展示、错误状态和完成结果回填。
- 页面刷新后，如果本地项目中仍有 `taskId`，会尝试继续轮询未完成的视频任务。
- 视频节点连接到另一个视频节点时可执行 Remix。
- 图像或文本上游会自动参与视频生成；Veo 路径可携带多张参考图。
- 支持全局视频提示词，生成时自动加到每个视频节点提示词前。
- 支持 Sora 角色管理：短视频上传、创建角色、搜索、编辑、删除以及 JSON 导入导出。
- 提供列表模式查看视频任务，显示进行中、成功和失败数量。
- 列表模式支持虚拟滚动、悬停预览、全选、批量删除和批量下载。

### 3.5 文本与分镜工程

- 文本节点既可直接生成内容，也可处理上游节点传来的内容。
- 支持系统提示词、自定义模板、上游图片和模型/提供商选择。
- 支持常用提示词预设的新增、分类、搜索、复制、导入和导出。
- 提示词预设分类包括收藏、角色、产品和品牌。
- “新建工程”支持粘贴文本或上传 `.txt`、`.srt` 文件。
- SRT 可按时间轴解析；普通文本可按段落或行拆分。
- 可调用文本模型将长文本分析为分镜，并对返回的 JSON 或普通文本做容错解析。
- 分镜预览中可编辑、排序、合并和清空镜头。
- 创建工程后，每个镜头会生成一个分组，默认包含剧本文本节点、提示词节点和视频节点，并自动连线。

### 3.6 音频生成

- 支持音频节点和独立的音频提供商配置。
- 默认兼容 OpenAI 风格 `/v1/audio/speech`，也可配置自定义端点。
- 支持模型、声音、输出格式和秒数等参数。
- 可处理二进制音频响应，也可解析 JSON 中的 URL 或 Base64 音频。
- 音频结果可在节点中播放并下载。

### 3.7 项目、工作流与生成历史

- 项目节点、连接、分组和视口在停止操作 5 秒后自动保存到 IndexedDB。
- 启动时自动恢复上一次本机项目。
- 完整项目可导出为 JSON，Blob 图片会转换为 Base64，因此可随项目文件迁移。
- 项目导入会恢复节点、连接、分组、视口、角色和应用设置。
- 默认导出会清空提供商 API Key，并且不包含角色 Token。
- 支持轻量工作流导出：保留结构和参数，清空生成媒体并重置运行状态。
- 支持本机工作流库，可保存、加载和删除常用节点结构；加载时会重建 ID 并放到当前视口中心，避免与现有节点冲突。
- 生成历史最多保留 80 条，覆盖图片、视频、音频和文本结果。
- 图片等大数据优先保存在 IndexedDB，localStorage 仅保留兼容数据。
- 历史项可预览、复制提示词、下载或重新放回画布。

### 3.8 保存与下载

- 在 HTTPS 或 `localhost` 等安全上下文中，可使用 File System Access API 选择固定文件夹，生成图片后自动写入该目录。
- 在局域网 HTTP 或不支持目录 API 的浏览器中，自动降级为浏览器下载，文件保存在当前访问用户电脑的下载目录。
- 生成文件名会清理非法字符，并带上节点、提示词、序号和扩展名信息。
- 单个节点支持下载；多选节点支持批量下载。
- 当前正式图片保存流程不再让 Vite 服务端写入服务器电脑目录。

### 3.9 设置与多提供商管理

- 图片、视频、文本、音频四类提供商分别管理。
- 每个提供商可配置名称、类型、Base URL、API Key、端点模式和模型列表。
- OpenAI 类型可选择标准 Chat 端点或自定义 Endpoint。
- 支持从提供商拉取模型列表，也可手工添加模型 ID 和显示名。
- 支持设置默认提供商。
- API 请求可选择“优先直连”或“优先代理”，一条路径失败后尝试另一条路径。
- 设置中可调整批量生成并发数量。
- 内置 Comfly 图片提供商结构，并为视频、音频提供 xwang 默认配置迁移逻辑。

## 4. 典型数据流

### 4.1 节点执行逻辑

```text
用户编辑节点
    -> 选择提供商、模型和参数
    -> 收集连入该节点的上游内容
    -> 按节点类型组装最终请求
    -> 调用图片/视频/文本/音频服务
    -> 更新 loading/progress/success/error 状态
    -> 写回节点内容
    -> 记录生成历史
    -> 触发本地项目自动保存
```

不同类型节点对上游数据的处理规则：

| 目标节点 | 上游内容的用途 |
| --- | --- |
| 图片节点 | 上游图片作为参考图；提示词中的 `@图N` 可筛选实际使用项 |
| 视频节点 | 上游文本拼入提示词，上游图片用于图生视频，上游视频用于 Remix |
| 文本节点 | 上游内容作为待处理素材，节点提示词作为处理指令 |
| 音频节点 | 节点提示词作为需要合成的文本或音频描述 |

### 4.2 本地持久化分层

| 存储位置 | 主要内容 | 特点 |
| --- | --- | --- |
| React 内存状态 | 当前节点、连接、分组、视口、选择状态、任务状态 | 响应界面交互，刷新后消失 |
| IndexedDB | 当前项目、工作流库、生成历史、目录句柄 | 容量较大，支持 Blob，适合媒体数据 |
| localStorage | API 设置、角色配置、提示词模板、兼容历史、欢迎状态 | 简单同步，但容量较小且不适合大图片 |
| JSON 文件 | 完整项目、轻量工作流、角色和提示词预设 | 用于备份、迁移和分享 |

### 5.3 当前架构特征

- 前端是单页应用，没有 React Router。
- 画布状态集中在 `App.tsx`，组件通过大量回调读写状态。
- API 层采用“统一调用函数 + 部分适配器”的混合结构。
- 项目自带的代理能力主要由 Vite 开发服务器中间件提供，不是独立生产后端。
- Docker 产物是 Nginx 静态站点，浏览器直接访问外部 API，或由部署方额外配置反向代理。

## 6. API 兼容与请求策略

### 6.1 图片和文本

- Gemini：使用 `/v1beta/models/{model}:generateContent`。
- OpenAI Chat：默认使用 `/v1/chat/completions`。
- OpenAI Images：根据模型、端点模式和参考图情况调用 generations 或 edits。
- 自定义接口：允许在 Base URL 后拼接用户配置的 Endpoint。
- 响应解析器会从标准字段、嵌套对象、Markdown、普通 URL 和 Base64 中提取图片。

### 6.2 视频

- Sora/OpenAI 任务式接口：创建任务后轮询状态。
- Veo：创建接口和查询接口使用独立路径及参数格式。
- Grok：使用视频任务接口，并兼容非流式返回。
- OpenAI 兼容流式接口：逐段读取响应，最终提取视频 URL。
- 请求失败时保留错误详情到节点，方便从界面复制和排查。

### 6.3 直连和代理

浏览器直连第三方 API 可能受 CORS、证书、网络代理或跨域图片下载限制。项目提供两种顺序：

- `direct-first`：优先浏览器直连，失败后尝试本地 Vite 代理。
- `proxy-first`：优先本地代理，失败后尝试直连。

Vite 开发服务器中提供 Chat、Images、模型列表和下载代理路由。静态生产部署不会自动拥有这些中间件，需要在网关或独立后端实现等价路由。

## 8. 程序员需要掌握的相关知识

### 8.1 画布坐标系

画布交互通常同时存在两套坐标：

- 屏幕坐标：鼠标相对浏览器视口的位置。
- 世界坐标：节点在无限画布中的逻辑位置。

转换关系为：

```ts
worldX = (screenX - viewport.x) / viewport.k;
worldY = (screenY - viewport.y) / viewport.k;
```

其中 `viewport.x/y` 是平移量，`viewport.k` 是缩放比例。新增节点、框选、拖拽、连线和小地图都必须使用一致的坐标换算，否则缩放后会出现位置漂移。

### 8.2 图结构与工作流

项目使用简化有向图：

```ts
interface Connection {
  id: string;
  fromNodeId: string;
  toNodeId: string;
}
```

执行节点时通过 `toNodeId` 查找所有入边，再读取对应上游节点。当前实现更接近“按用户触发执行并临时收集上游”的数据流图，并不是带拓扑排序、循环检测、缓存和调度状态机的完整工作流引擎。

后续若要支持“一键运行整张图”，需要补充：

- 有向无环图校验和循环检测。
- 拓扑排序与依赖完成判断。
- 节点输入/输出端口类型约束。
- 失败重试、取消传播和断点续跑。
- 结果缓存与脏节点判断。

### 8.3 React 状态与异步闭包

长时间生成任务容易读取到旧的 React state。项目使用 `nodesRef`、`connectionsRef`、`appSettingsRef` 等引用保存最新值，让轮询和回调在异步完成时仍能访问当前状态。

维护时需要注意：

- UI 更新使用 state，异步任务读取最新值使用 ref。
- 新增关键 state 时，要判断是否也需要同步 ref。
- Blob URL 使用后应适时 `URL.revokeObjectURL`，否则长时间使用会积累内存。
- 组件卸载或节点删除时要中止请求、清除定时器。

### 8.4 Blob、Base64 与 Object URL

- `Blob`：适合保存二进制媒体，也是 IndexedDB 的合适数据类型。
- Base64/Data URL：容易写入 JSON，但体积通常比二进制大约增加三分之一。
- `blob:` Object URL：只是当前页面会话中的临时引用，不能直接用于跨会话持久化。

因此项目自动保存 Blob；项目导出时转换为 Base64；导入后再还原 Blob 并创建新的 Object URL。

### 8.5 IndexedDB 与 localStorage

- localStorage 同步、简单，但容量小，保存大图容易超限并阻塞主线程。
- IndexedDB 异步、容量更大，可直接保存 Blob，适合项目和生成历史。
- 两者都按浏览器 Origin 隔离；域名、协议或端口变化后会被视为另一份数据。
- 清理浏览器站点数据会删除项目和历史，因此重要内容仍应导出 JSON 备份。

### 8.6 浏览器安全上下文

`showDirectoryPicker()` 等 File System Access API 通常只允许在 HTTPS 或 localhost 中使用，并且必须由用户手势触发。局域网 IP 的普通 HTTP 页面不能取得访问者电脑任意文件夹的写权限，只能退回浏览器下载。

这也是前端程序无法“让服务器替访问者选择本机目录”的根本原因：浏览器和服务器位于不同的安全边界。

### 8.7 CORS 与代理

CORS 是浏览器限制，不等于目标 API 不可用。常见处理方式有：

1. API 服务端正确返回 `Access-Control-Allow-Origin`。
2. 同源后端代发请求。
3. 开发期使用 Vite 中间件代理。
4. 生产期在 Nginx、网关或独立服务中实现代理，并限制允许访问的目标地址。

开放式代理会带来 SSRF、密钥泄露和带宽滥用风险，生产环境不能直接照搬无限制的开发代理。

### 8.8 API 密钥安全

- 前端输入的 API Key 最终会存在浏览器内存或 localStorage，并由浏览器发往目标 API。
- `VITE_` 环境变量会被打进静态资源，任何访问者都可能查看。
- 项目导出默认脱敏是必要措施，但不能替代后端密钥托管。
- 公开部署应让服务端持有密钥，前端只拿短期令牌或调用受控业务接口。
- 日志中不要打印完整 Key、Token、带签名 URL 或包含敏感信息的请求体。

### 8.9 任务轮询与流式响应

任务式视频接口通常分为创建、查询和下载三步。可靠实现需要考虑：

- 固定或退避轮询间隔。
- 总超时和单次请求超时。
- 临时网络错误重试。
- 页面刷新后的任务恢复。
- 用户取消时使用 AbortController 停止任务。
- 服务端成功但 URL 字段不统一时的兼容解析。

流式接口则需要处理分块边界：一个 JSON 对象可能跨多个网络 chunk，不能假设每次 `read()` 都返回完整消息。

### 8.10 前端性能

项目已经采用视口裁剪、列表虚拟滚动、5 秒防抖自动保存和批量并发限制。继续优化时应重点关注：

- 大量节点移动导致的全局 state 更新和重渲染。
- Base64 和大 Blob 带来的内存峰值。
- 视频节点常驻渲染造成的解码与网络占用。
- 生成历史和项目导出时的串行转换成本。
- 本地 ONNX 抠图对低配设备主线程和内存的压力。
- 连接线 SVG 在节点和边数量很大时的绘制成本。

## 9. 当前限制与技术债

1. `App.tsx` 约 5,500 行，承担了状态、业务、网络编排和大量 UI，维护成本较高。
2. `package.json` 没有测试、Lint、格式化或独立类型检查脚本；Vite 构建可以通过，但当前独立 TypeScript 检查仍有错误。
3. 代码中仍有较多 `any`、`@ts-ignore`、浏览器弹窗和调试日志，类型边界与错误体验可继续完善。
4. API 适配层尚未完全统一；Gemini 适配器类仍是占位实现，实际逻辑直接位于 `geminiService.ts`。
5. 工作流缺少完整的拓扑调度、循环检测、端口类型和依赖缓存。
6. 只有撤销栈，没有完整重做机制；撤销覆盖范围也需要持续核对。
7. 浏览器本地数据没有账号、云同步、版本冲突和多人协作能力。
8. 静态 Docker 部署不会运行 `vite.config.ts` 中的开发中间件，生产代理要单独建设。
9. 目录自动保存依赖浏览器实现和安全上下文，不同浏览器能力不一致。
10. 部分源码注释和旧字符串存在乱码痕迹，应统一为 UTF-8，并在编辑器和 Git 中固定编码。
11. 导出的完整项目可能因嵌入大量 Base64 图片而非常大，需要考虑流式导出、ZIP 或独立资源清单。
12. 本地 API Key 存储适合个人工具，不适合直接作为公开 SaaS 的安全方案。

## 12. 总结

X-tapnow 已经具备较完整的 AI 多媒体节点工作台能力：它能在无限画布中组织图片、视频、文本和音频，连接上下游素材，配置多种模型接口，批量执行生成任务，并在本机保存项目、工作流和历史结果。分镜工程、视频任务恢复、本地抠图、多角度图片、视觉合成和便携版构建，使它超出了普通 AI 接口演示项目的范围。

从工程角度看，当前项目适合作为个人或局域网创作工具继续迭代。若要发展为稳定的多人生产系统，优先事项应是拆分超大的应用组件、建立自动化测试、统一适配器协议，并将密钥与代理能力迁移到受控后端。
